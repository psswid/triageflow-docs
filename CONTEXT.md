# TriageFlow

AI-assisted patient pre-screening demonstration system. A two-week portfolio project simulating a medical triage pipeline with synthetic data and LLM-powered analysis. Primary goal is demonstrating full-stack development proficiency with Symfony + React + AI — not medical accuracy.

The frontend serves dual duty: an authenticated SPA (the triage tool itself) and a public-facing business website with marketing pages. The public site provides landing, about, and legal pages; the authenticated app is the functional core. Both share a unified design system (medical triage color palette), i18n (EN + PL), and dark mode.

## Language

**Triage Submission**:
A complete symptom report submitted by a User for AI-assisted analysis. Contains the full conversation history (initial complaint + AI follow-up questions + User answers) and the final AI triage result. A single entity — no separate TriageResult.
_Avoid_: Intake, case, symptom questionnaire

**User**:
A self-registered person who creates Triage Submissions and views their own results. Serves double duty as both the system actor and the "patient" role in the triage data — the User reports their own symptoms. Accounts are demo-only; all submissions are synthetic.
_Avoid_: Patient, submitter

**Admin**:
An authenticated person who monitors the live simulation via the dashboard — views all Triage Submissions flowing through the pipeline, triggers synthetic case generation, and checks system statistics. Manages Users but cannot edit or override Triage Submissions (those belong to the User who created them). Can impersonate Users via login-as for debugging.
_Avoid_: Administrator, reviewer, moderator

**Initial Symptom Description**:
The free-text description a User enters to begin the triage interview. Written in natural language ("my head is going to explode"), not structured form fields. This is the first message in a Triage Submission's conversation history.
_Avoid_: Chief complaint, initial intake, opening statement

**Turn**:
One complete exchange in the triage interview: a User message followed by the AI's response. The interview consists of the Initial Symptom Description plus up to 3 Turns — the AI can produce its final triage result in any Turn (1, 2, or 3) when it has sufficient information. If the AI hasn't produced a result by Turn 3, the backend forces a final result from the conversation gathered so far.

**Conversation History**:
The full transcript of a Triage Submission's interview — the Initial Symptom Description plus all Turns — stored in the entity. Each message has a character limit to prevent token bloat (Initial Symptom Description: 500 chars, User answers: 300 chars, AI responses: 1000 chars). The AI receives the complete history on each Turn to maintain context.

**TriageOutcome**:
The final AI analysis within a Triage Submission — not a separate entity. Contains the recommended specialist, urgency level, and a brief medical justification. Is `null` while the interview is in progress; set when the AI produces its final result. Packaged as a value object inside the Triage Submission aggregate.
_Avoid_: TriageResult, diagnosis, conclusion

**Synthetic Case**:
A Triage Submission where `isSynthetic = true` — the Initial Symptom Description was generated by the scheduler or a manual Admin trigger rather than a real User. Flows through the exact same pipeline as user-submitted cases (AI-driven interview → triage result). Includes a cooldown between Turns to simulate realistic human typing speed.
_Avoid_: Fake case, auto-generated submission, bot submission
